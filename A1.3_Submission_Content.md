## 4. Reflections: Challenges

The hardest part of this version was accepting that client-side authentication can only ever be a
demonstration of the right structure, not real protection, and then building it so the structure is
genuinely right anyway.

The specific problem that took longest was authorisation. My first instinct was to hide the Admin
link from members in the navigation bar, which looks correct until you type `/admin` into the
address bar and the page loads regardless. Moving the decision into a `router.beforeEach` guard, and
declaring the permitted roles as route metadata, meant every route was checked the same way whether
it was reached by clicking, by typing a URL, or by a hard refresh. Handling the refresh case
properly forced a second change: the signed-in user lives in memory, so a reload emptied it and
bounced the user to the login page. The guard now re-reads and re-validates the stored session
before deciding, which also gave a natural place to expire stale sessions.

Passwords were the other thing that stretched me. Storing them as-is in localStorage would have
satisfied the brief, but the whole point of BR (C.1) is confidentiality, and the realistic threat for
a browser-only app is a shared or borrowed laptop. I used the Web Crypto API to derive a
PBKDF2-SHA256 hash with a random per-account salt and 150,000 iterations, and compared hashes in
constant time. Learning that `crypto.subtle` is asynchronous and only available in a secure context
changed the shape of the app's startup, because the first render now has to wait on a promise —
which is why there is a loading panel in `index.html` rather than a blank screen.

Testing the rating aggregation also taught me something. My first version recalculated the average
by pushing every submission, which meant one member rating the same group twice counted twice. I
changed it to upsert on `(activityId, userId)` and verified it by registering two accounts, rating
the same group 5 and 3, and confirming the card showed 4 from two ratings rather than a drifting
number.

## 5. Security Reflection (BR C.4)

*This section is required if you attempted BR C.4.*

**Threat model.** The application is entirely client-side, as the brief allows, so its realistic
threats are: a stored payload that executes when it is rendered back (XSS), passwords being readable
by anyone with access to the browser profile, someone reaching a page their role should not allow,
and data in localStorage being edited by hand in DevTools.

**Cross-site scripting.** I treated this in three layers rather than relying on one. First, the
application never uses `v-html`, `innerHTML`, `eval` or `new Function` anywhere — all user content
is rendered through `{{ }}` interpolation, which Vue escapes by default. Second, `sanitizeText` in
`src/utils/sanitize.js` strips HTML tags, script-bearing URL schemes (`javascript:`, `data:`,
`vbscript:`), inline event handlers and control characters, and caps length, before any value is
written to storage. Third, an `isSafe` validation rule rejects input containing markup outright with
a visible error, rather than silently rewriting what the user typed — so a member who pastes
`<img src=x onerror=alert(1)>` into a review is told why it was refused. I verified this in the
browser: the payload is refused at the form, and nothing resembling an `img` tag is ever created.

**Password handling.** Passwords are never stored or compared in plain text. Each account gets a
16-byte random salt, and the password is put through PBKDF2-SHA256 with 150,000 iterations using the
Web Crypto API; only the salt and derived hash are persisted. Hashes are compared in constant time
so the comparison leaks nothing about how much of the value matched. The public user object handed
to the UI deliberately omits the salt and hash, so neither can reach a component or the admin table.

**Authentication and session handling.** Sessions carry an explicit expiry (two hours) and are
re-validated on every navigation; an expired session, or one naming a user who no longer exists, is
discarded rather than trusted. Five failed sign-ins lock an account for fifteen minutes. The failure
message is identical whether the email is unknown or the password is wrong, so the form cannot be
used to discover which accounts exist. The post-login redirect only follows internal paths, so a
crafted `?redirect=` value cannot turn the sign-in form into an open redirect.

**Authorisation.** Role checks live in the router guard with the permitted roles declared as route
metadata, not in the template that draws the navigation. Hiding the Admin link is a convenience;
refusing the route is the control.

**Untrusted local storage.** Everything read back from localStorage is treated as untrusted input
and re-validated against an expected shape before use, because the user can edit it freely in
DevTools. A malformed or tampered entry is discarded and the app falls back to a safe default rather
than crashing or trusting it. Writes are wrapped so a blocked or full storage (private browsing,
quota exceeded) degrades to an in-memory fallback and a visible warning instead of throwing.

**Client-side validation.** Every form validates on blur and again on submit, using shared rules for
format (email, name), composition strength (password: length, upper, lower, digit), cross-field
comparison (password confirmation), numeric range (distance, duration, rating) and length caps.

**Seeded demo credentials.** The sign-in page publishes two demo logins so both roles can be
assessed without registering an account first. That is a deliberate choice for this submission, not
an oversight: without a coordinator login the role-based pages cannot be reached at all. It is
labelled as marking access on the page itself, and it is the first thing that would be removed
before any real deployment.

**Testing my own authorisation, and what it found.** Rather than assume the role check held, I
attacked it. Signed in as an ordinary member, I opened DevTools and ran three lines: read the stored
account list, change my own `role` from `member` to `admin`, write it back. The router guard then
admitted me to `/admin`. No password was required at any point, because the guard trusts the stored
record and the record was mine to edit.

That is not a flaw in the guard. It is the ceiling of the architecture: the check runs on the machine
the attacker controls, so no amount of hashing, validation or guarding changes the outcome.

**The control I added in response.** Account records are now written with an HMAC-SHA256 tag over
their contents. At startup the tag is recomputed and compared in constant time; if the stored data
was edited by hand the tag no longer matches, and the app discards the session and signs the user
out instead of trusting the record. Re-running the identical attack now fails: the integrity check
returns false, the current user becomes null, and `/admin` is refused.

I want to be precise about what that is worth. The HMAC key ships inside the JavaScript bundle, so
anyone willing to read the source can recompute a valid tag for edited data. The control raises the
cost of the attack from trivial to deliberate and it reliably catches accidental corruption, but it
is not a security boundary. A value the user's own machine can compute is a value the user can
forge. I have implemented it as defence in depth and labelled it as such in the source, rather than
presenting it as protection it cannot provide.

**What a genuinely secure version requires.** The fix is architectural, not a better client-side
trick. Authorisation has to happen somewhere the user cannot reach:

- **Identity** through an external provider such as Firebase Authentication, so the application never
  handles a password directly.
- **Roles as signed token claims** rather than stored fields. Editing a claim in DevTools invalidates
  the signature and the server rejects the request.
- **Data access enforced server-side**, for example Firestore security rules of the form
  `allow read: if request.auth.token.role == 'admin'`, evaluated on the provider's infrastructure
  rather than in the browser.
- **Privileged operations behind serverless functions**, so the client requests an action instead of
  performing it.
- **Session tokens in HttpOnly, Secure, SameSite cookies** rather than localStorage, because
  localStorage is readable by any successful XSS while an HttpOnly cookie is not.
- **Rate limiting and lockout enforced server-side.** Mine currently lives in localStorage, where it
  can be removed by deleting a key.

The client-side validation and sanitisation described above stay in that design. They stop being the
control and become what they should always have been: user experience, and one more layer that an
attacker has to get through. Everything they check would be re-checked on the server, because input
that has only been validated in the browser has not been validated at all.
